# Backend Schema — Supabase (Production Phase)

Multi-tenant by design — every table is scoped by `user_id`. Must correctly support ≥ 2 concurrent users with fully isolated credentials, Q&A caches, and application logs. This schema is additive: new domains/columns can be introduced without breaking existing rows (see §6, dynamic schema notes).

---

## 1. Entity Overview

```
users ──┬── telegram_links (1:1)
        ├── workday_credentials (1:1, encrypted)
        ├── qa_answers (1:many)
        ├── applications (1:many)
        ├── resumes (1:many)
        └── notifications_log (1:many)

job_links (independent pool, tagged by domain, referenced by applications)
```

---

## 2. Table DDL

### 2.1 `users`
Core identity record. One row per job seeker.

```sql
create table users (
  id                uuid primary key default gen_random_uuid(),
  email             text unique not null,
  full_name         text,
  domain            text not null,           -- e.g. 'software_engineer' — drives job-link matching
  domain_secondary  text[],                   -- optional additional domains
  status            text not null default 'active', -- active | paused | disabled
  daily_apply_cap   int not null default 20,
  created_at        timestamptz not null default now(),
  updated_at        timestamptz not null default now()
);
```

### 2.2 `telegram_links`
Maps a Telegram chat to a user. Created at onboarding via QR deep-link.

```sql
create table telegram_links (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references users(id) on delete cascade,
  telegram_chat_id  bigint not null unique,
  telegram_username text,
  link_token    text unique not null,        -- the token embedded in the onboarding QR deep-link
  linked_at     timestamptz,
  created_at    timestamptz not null default now()
);
```

### 2.3 `workday_credentials`
Stores the Workday login used for auto-login. **Encrypted at rest** — use Supabase Vault / pgsodium column encryption, never plaintext.

```sql
create table workday_credentials (
  id              uuid primary key default gen_random_uuid(),
  user_id         uuid not null references users(id) on delete cascade unique,
  workday_email   text not null,
  workday_password_encrypted bytea not null,   -- pgsodium/vault-encrypted, app decrypts at runtime
  tenant_domain   text,                        -- e.g. 'adobe.wd5.myworkdayjobs.com', if account is tenant-specific
  created_at      timestamptz not null default now(),
  updated_at      timestamptz not null default now()
);
```

### 2.4 `resumes`
```sql
create table resumes (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references users(id) on delete cascade,
  label         text not null,               -- e.g. "General", "Backend-focused"
  file_url      text not null,               -- Supabase Storage path/URL
  keywords      text[],                      -- for JD-keyword matching
  is_default    boolean not null default false,
  created_at    timestamptz not null default now()
);
```

### 2.5 `qa_answers`
The permanent per-user Q&A memory. This is the core of "ask once, remember forever."

```sql
create table qa_answers (
  id                uuid primary key default gen_random_uuid(),
  user_id           uuid not null references users(id) on delete cascade,
  question_raw      text not null,            -- verbatim question text as scanned
  question_normalized text not null,          -- lowercased/punctuation-stripped, used for fuzzy match
  answer            text not null,
  field_type        text,                     -- text | dropdown | radio | checkbox | multiselect
  source            text not null,            -- 'cache' | 'resume_inferred' | 'user_provided'
  is_compliance_sensitive boolean not null default false,  -- work auth / visa / EEO flag
  company            text,                    -- optional: company the question originated from
  created_at        timestamptz not null default now(),
  updated_at        timestamptz not null default now(),
  unique (user_id, question_normalized)
);

create index idx_qa_answers_user_fuzzy on qa_answers using gin (question_normalized gin_trgm_ops);
-- requires: create extension if not exists pg_trgm;
```

### 2.6 `job_links`
The domain-tagged pool the bot draws from to notify users.

```sql
create table job_links (
  id            uuid primary key default gen_random_uuid(),
  url           text not null unique,
  company       text,
  role_title    text,
  domain        text not null,               -- must match users.domain taxonomy
  posted_at     timestamptz,
  is_active     boolean not null default true,
  created_at    timestamptz not null default now()
);

create index idx_job_links_domain on job_links(domain) where is_active;
```

### 2.7 `applications`
The application log — one row per (user, job) attempt.

```sql
create table applications (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references users(id) on delete cascade,
  job_link_id   uuid references job_links(id),
  url           text not null,
  company       text,
  role_title    text,
  status        text not null,     -- pending | eligible | ineligible | submitted | needs_review | failed
  resume_id     uuid references resumes(id),
  submitted_at  timestamptz,
  screenshot_pre_url  text,
  screenshot_post_url text,
  failure_reason text,
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);

-- Dedup guard: prevent re-applying to same company within a rolling window (app-enforced query, see §5)
create index idx_applications_user_company_date on applications(user_id, company, created_at);
```

### 2.8 `notifications_log`
Audit trail of every Telegram message sent (approval requests, escalations, results).

```sql
create table notifications_log (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references users(id) on delete cascade,
  application_id uuid references applications(id),
  message_type  text not null,   -- 'job_match' | 'login_confirm' | 'unknown_question' | 'result'
  message_text  text not null,
  direction     text not null,   -- 'outbound' | 'inbound'
  sent_at       timestamptz not null default now()
);
```

## 3. Row-Level Security (required for multi-tenancy)

Enable RLS on every user-scoped table and restrict to the owning user's service-role-authenticated bot session (the bot backend uses the Supabase service role, so RLS mainly protects against any future direct client access):

```sql
alter table users enable row level security;
alter table telegram_links enable row level security;
alter table workday_credentials enable row level security;
alter table qa_answers enable row level security;
alter table applications enable row level security;
alter table resumes enable row level security;
alter table notifications_log enable row level security;

-- Example policy (repeat pattern per table)
create policy "user_owns_row" on qa_answers
  for all using (auth.uid() = user_id);
```

## 4. Fuzzy Matching Query Pattern

```sql
select *, similarity(question_normalized, $1) as score
from qa_answers
where user_id = $2
  and question_normalized % $1        -- pg_trgm similarity operator
order by score desc
limit 1;
```
Application code applies a configurable similarity threshold (e.g. `score >= 0.55`) before treating it as a hit; below threshold falls through to resume-inference, then to the Telegram escalation path.

## 5. Dedup + Daily Cap Enforcement (app-level, backed by schema)

```sql
-- Has this user applied to this company in the last 60 days?
select exists (
  select 1 from applications
  where user_id = $1 and company = $2
    and created_at > now() - interval '60 days'
);

-- Applications submitted today for this user
select count(*) from applications
where user_id = $1 and status = 'submitted'
  and created_at::date = current_date;
-- compare against users.daily_apply_cap before queuing another
```

## 6. Dynamic Schema Notes

- **Adding a new domain** (e.g. "Data Scientist") requires no migration — `users.domain` and `job_links.domain` are free text, matched exactly (or via a lookup table if a controlled taxonomy is later required — see below).
- **Optional hardening for later:** replace free-text `domain` with a `domains` lookup table + FK if the taxonomy needs to be governed rather than free text. Not required for the 2-user MVP.
- **Adding new Q&A fields** never requires a migration — `qa_answers` is schema-flexible by design (question/answer/type as generic columns), so any new Workday question type is stored without a DDL change.
- **Compliance flag** (`is_compliance_sensitive`) should be set `true` automatically by the application layer whenever the question matches a known compliance keyword list (visa, sponsorship, authorized to work, veteran, disability, race, gender, EEO) — this is an app-layer rule, not a DB constraint.
