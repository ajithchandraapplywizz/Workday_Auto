# TRD.md --- Workday Auto-Apply Bot

**Project:** Workday Auto-Apply Bot\
**Stack:** Node.js + Playwright\
**Primary Runtime:** Node.js CLI / headed Chromium\
**Backend (Production):** Supabase\
**Messaging (Production):** Telegram Bot API\
**Scope:** Workday ATS only\
**Document Status:** Technical Requirements --- Draft v1\
**Source Documents:** PRD, RD, Workflow, UI/UX Specification, Backend
Schema, Telegram Bot Setup, AGENTS.md / CLAUDE.md

------------------------------------------------------------------------

## 1. Purpose

This Technical Requirements Document (TRD) converts the product
requirements into an implementation-level contract for the coding agent.

The system must provide one reusable Workday application engine with two
execution shells:

``` text
Local Phase
Terminal + local config/YAML + CSV
        │
        ▼
┌───────────────────────────────┐
│ Shared Workday Core Engine     │
│ discovery → scan → plan       │
│ → fill → verify → submit      │
└───────────────────────────────┘
        ▲
        │
Production Phase
Telegram + Supabase
```

The Production Phase must not create a second application engine. It
must reuse the Local Phase core engine through injected data stores and
human-interaction adapters.

------------------------------------------------------------------------

# 2. Technical Principles

## 2.1 Workday-only boundary

The application must process Workday career/application URLs only.

Allowed:

-   Workday-hosted career sites
-   Workday application wizard pages
-   Workday authentication/application states

Explicitly excluded:

-   Greenhouse
-   Lever
-   Ashby
-   iCIMS
-   SmartRecruiters
-   Generic ATS abstractions carried over from previous implementations

If an existing module contains multi-ATS logic, it must not be
reactivated for this build.

------------------------------------------------------------------------

## 2.2 DOM-first decision architecture

All application decisions must originate from:

1.  DOM
2.  Accessibility tree
3.  Semantic Playwright locators
4.  Explicit page-state metadata

Screenshots are audit artifacts only.

The engine must never use:

-   OCR for field discovery
-   computer vision for clicking
-   pixel coordinates
-   image similarity to identify fields
-   screen-position assumptions

------------------------------------------------------------------------

## 2.3 Source-of-truth answer hierarchy

For every question:

``` text
Compliance-sensitive?
        │
        ├─ Existing explicit human answer → use it
        │
        └─ No explicit human answer → human fallback
                         │
                         ▼
                 never auto-infer
```

For normal factual questions:

``` text
1. User Q&A cache
2. Structured profile/resume data
3. Human fallback
4. Never invent
```

# 5. Runtime Modes

## 5.1 Local

Local mode must use:

``` text
headless: false
```

This is mandatory and must not be configurable to `true`.

Expected command pattern:

``` bash
node cli.mjs --mode=local
```

Optional:

``` bash
node cli.mjs --mode=local --confirm-submit
```

`--confirm-submit` changes only the final-submit behavior. It does not
change field discovery or answer rules.

------------------------------------------------------------------------

## 5.2 Production

Production mode adds:

``` text
Telegram
   │
   ▼
Supabase
   │
   ▼
Shared Workday Engine
```

Expected conceptual command:

``` bash
node cli.mjs --mode=production
```

Production jobs must run independently per user.

------------------------------------------------------------------------

# 6. Browser Requirements

## 6.1 Playwright

Playwright is the only browser automation layer.

Browser initialization must:

-   launch Chromium
-   use headed mode in Local Phase
-   create an isolated browser context per application/user run
-   avoid sharing authentication state between users
-   close contexts cleanly on completion/failure

------------------------------------------------------------------------

## 6.2 Locator priority

Every interaction must use this priority:

``` text
1. getByRole()
2. getByLabel()
3. [data-automation-id]
4. getByText() / :has-text()
5. Other semantic DOM locator only if justified
```

Never use:

-   absolute XPath
-   screen coordinates
-   generated CSS class names
-   `nth()` as the primary semantic identification mechanism
-   blind click sequences

If a locator is ambiguous, stop and diagnose rather than guessing.

------------------------------------------------------------------------

# 7. Link Intake

## 7.1 Input

Local input:

``` text
targets.txt
```

Format:

``` text
https://company.wd5.myworkdayjobs.com/en-US/company/job/123
https://company.wd5.myworkdayjobs.com/en-US/company/job/456 | Example Company
```

One URL per line.

Blank lines and comments may be ignored.

------------------------------------------------------------------------

## 7.2 Validation

The discovery module must:

1.  Parse the line.
2.  Extract URL.
3.  Validate URL syntax.
4.  Validate that the hostname belongs to an allowed Workday pattern.
5.  Preserve optional company label.
6.  Log invalid entries.
7.  Continue processing valid entries.

Invalid input must never crash the batch.

Example warning:

``` text
⚠ Skipping malformed target: <line>
Reason: invalid URL
```

------------------------------------------------------------------------

# 8. Authentication Architecture

## 8.1 Authentication state detection

After opening the job URL, the system must classify the page as one of:

``` text
GUEST_APPLY
SIGN_IN_REQUIRED
SIGN_UP_REQUIRED
AUTH_POPUP
APPLICATION_ALREADY_STARTED
APPLICATION_FORM
UNKNOWN
```

Detection must be DOM/accessibility based.

------------------------------------------------------------------------

## 8.2 Existing authentication reuse

Existing sign-in/sign-up logic is an implementation dependency.

Do not rebuild an already-working authentication implementation unless
it is required to satisfy the new engine contract.

The integration boundary should look conceptually like:

``` js
await workday.authenticate({
  page,
  credentials,
  state
});
```

Authentication must return the detected post-auth state rather than
blindly retrying.

------------------------------------------------------------------------

## 8.3 Post-auth redirect

After login/signup:

``` text
authenticate()
       │
       ▼
wait for stable state
       │
       ▼
detect page state again
```

Never assume:

``` text
login success → specific URL
```

The resulting state may be:

-   job page
-   application wizard
-   profile page
-   account page
-   error/interstitial
-   already-started application

------------------------------------------------------------------------

# 9. DOM Scanner

## 9.1 Scanner output

The scanner should produce normalized field objects.

Conceptual structure:

``` js
{
  id,
  label,
  normalizedLabel,
  required,
  fieldType,
  options,
  value,
  disabled,
  readonly,
  locatorMetadata,
  section,
  complianceSensitive
}
```

The scanner must not directly decide the answer.

------------------------------------------------------------------------

## 9.2 Accessibility tree

Where available, use:

``` js
await page.accessibility.snapshot();
```

Combine accessibility information with DOM inspection.

The accessibility tree is supplementary to semantic DOM locators, not a
replacement for them.

------------------------------------------------------------------------

## 9.3 Question normalization

Normalization should include:

-   trim whitespace
-   lowercase
-   normalize repeated spaces
-   remove irrelevant punctuation
-   preserve meaningful words
-   normalize common equivalent formatting

Example:

``` text
"What is your current job title?"
```

becomes approximately:

``` text
what is your current job title
```

The raw question must still be retained for auditability.

------------------------------------------------------------------------

# 10. Fuzzy Q&A Matching

## 10.1 Matching requirements

Every scanned question must be checked against the current user's Q&A
store.

Recommended flow:

``` text
normalize(question)
       │
       ▼
candidate lookup
       │
       ▼
similarity score
       │
       ├── score >= configured threshold → candidate
       │
       └── score < threshold → cache miss
```

The threshold must be configurable.

Suggested starting value:

``` text
0.55
```

It must be tested and tuned against real Workday questions rather than
treated as universally correct.

------------------------------------------------------------------------

## 10.2 User isolation

The Q&A lookup must always include:

``` text
user_id
```

Production must never query a global Q&A cache.

Incorrect:

``` text
findAnswer(question)
```

Preferred interface:

``` text
findAnswer(userId, question)
```

------------------------------------------------------------------------

# 11. Compliance-Sensitive Questions

The system must identify at least:

-   work authorization
-   authorized to work
-   visa
-   visa sponsorship
-   sponsorship
-   government employment
-   veteran status
-   disability
-   race
-   ethnicity
-   gender
-   EEO
-   voluntary disclosure

These categories must be treated conservatively.

## Rule

If no explicit human-provided answer exists for the current user:

``` text
DO NOT:
- infer
- fuzzy-fill
- resume-infer
- guess
- auto-submit
```

Instead:

``` text
pause → request human answer → persist → continue
```

A cached answer is valid only if it was explicitly sourced from the
human.

------------------------------------------------------------------------

# 12. Resume/Profile Inference

Resume/profile inference is permitted only for factual, non-compliance
fields.

Examples:

``` text
full name
email
phone
education
school
graduation year
work experience
job title
LinkedIn URL
portfolio URL
skills
```

The engine must not invent values.

If a requested fact is absent:

``` text
no value → human fallback
```

# 14. Field Handling

## 14.1 Text fields

Before filling:

``` text
exists → visible/enabled check → fill → verify
```

Verification must inspect the actual DOM value.

------------------------------------------------------------------------

## 14.2 Searchable dropdown

Required flow:

``` text
locate
→ click
→ identify search input
→ type search term
→ wait for options
→ inspect options
→ exact/semantic option match
→ select
→ verify selected value
```

Example requirement:

``` text
United States of America +1
```

The implementation must search the dropdown options and select the exact
semantic option rather than assuming an index.

------------------------------------------------------------------------

## 14.3 Cascading dropdown

Required:

``` text
select parent
→ wait for child state change
→ re-scan child options
→ select child
→ verify
```

Do not assume the child options are immediately available.

------------------------------------------------------------------------

## 14.4 Radio groups

Select by:

``` text
explicit label/value
```

Never:

``` text
first option
second option
nth option
```

------------------------------------------------------------------------

## 14.5 Checkboxes

Flow:

``` text
locate
→ inspect checked state
→ click only if necessary
→ verify checked === true
```

------------------------------------------------------------------------

## 14.6 File upload

Use:

``` js
locator.setInputFiles(filePath)
```

Never automate the operating-system file picker.

------------------------------------------------------------------------

## 14.7 Read-only fields

If a field is:

``` text
readonly
```

or prefilled and not intended for modification:

``` text
inspect → verify → do not overwrite
```

------------------------------------------------------------------------

# 15. Required-Field Verification

Before transition:

``` text
scan page
→ identify required fields
→ verify each required field has valid value
```

If any required field is unresolved:

``` text
retry bounded fill cycle
```

Recommended:

``` text
max 2–3 attempts
```

After bounded retries:

``` text
diagnostic capture
→ clean failure/needs_review
```

Never enter an infinite retry loop.

------------------------------------------------------------------------

# 16. Page Transition

After clicking:

``` text
Save and Continue
```

the engine must:

1.  capture pre-transition audit screenshot if configured
2.  verify button exists
3.  click
4.  wait for Workday loading state to settle
5.  wait for next meaningful DOM state
6.  re-detect current state
7.  re-scan the DOM

Do not rely exclusively on URL changes.

Do not use a fixed page count.

------------------------------------------------------------------------

# 17. State Detection

State detection must be performed repeatedly.

Canonical states:

``` text
MY_INFORMATION
MY_EXPERIENCE
APPLICATION_QUESTIONS
VOLUNTARY_DISCLOSURES
REVIEW
CONFIRMATION
AUTH
UNKNOWN
```

The actual Workday tenant may omit or add stages.

Detection signals may include:

-   visible heading
-   semantic heading role
-   progress indicator
-   URL
-   visible navigation controls
-   known section labels

Priority should favor rendered semantic content over URL assumptions.

------------------------------------------------------------------------

# 18. Unknown State Policy

If no known state can be confidently identified:

``` text
capture screenshot
capture DOM/accessibility diagnostics
capture URL
capture visible heading
capture timestamp
log failure
close cleanly
```

Never guess the next action.

------------------------------------------------------------------------

The engine should maintain an in-memory application ledger during a run.

Conceptual:

``` js
{
  question: "...",
  normalizedQuestion: "...",
  intendedValue: "...",
  actualValue: "...",
  source: "cache|resume_inferred|user_provided",
  verified: true

```

This ledger is required for Review cross-checking and auditability.

The ledger must not contain passwords or other secrets.

# 22. Confirmation Detection

After submission, detect a confirmation state using DOM/semantic
content.

Examples of acceptable evidence:

-   confirmation heading
-   success message
-   application submitted state
-   Workday confirmation content

Do not use screenshot interpretation.

If confirmation cannot be established:

``` text
status = needs_review
```

rather than falsely reporting success.

------------------------------------------------------------------------

# 23. Failure Handling

All top-level runs require an exception boundary.

On unhandled exception:

``` text
catch
→ record URL
→ timestamp
→ error message
→ stack
→ screenshot
→ close browser/context
→ report failure
```

No:

``` text
silent catch
```

No:

``` text
infinite relaunch loop
```

A batch runner may continue to the next independent URL after the
current run is safely closed.

# 30. Supabase Access Model

The server may use the Supabase service role for backend operations, but
application logic must still enforce:

``` text
current user_id == target user_id
```

Every query that handles user data must be explicitly scoped.

Examples:

``` text

Applications → WHERE user_id = currentUser
Credentials → WHERE user_id = currentUser
Telegram link → current linked user
```

Never use a shared/global application state.

# 32. Telegram Deep-Link Onboarding

The QR contains:

``` text
https://t.me/<bot_username>?start=<opaque_token>
```

Flow:

``` text
Generate token
→ store pending link
→ generate QR
→ user scans
→ Telegram /start token
→ bot validates token
→ bot requests email
→ email maps to user
→ chat_id stored
→ login/app workflow starts
```

The QR is a deep-link mechanism, not Telegram's native account-login QR
protocol.

------------------------------------------------------------------------

# 38. Concurrent User Isolation

Minimum Production acceptance test:

``` text
User A starts Job A
User B starts Job B
```

Both may be active simultaneously.

The system must prove:

``` text
A credentials ≠ B credentials
A Q&A ≠ B Q&A
A Telegram chat ≠ B Telegram chat
A application log ≠ B application log
A pending question ≠ B pending question
```

No global mutable singleton may contain user-specific runtime state.

Use per-run/per-user context objects.

------------------------------------------------------------------------

# 39. Daily Application Cap

Each user has:

``` text
daily_apply_cap
```

Before starting a new application:

``` text
count today's submitted applications
        ↓
count < daily_apply_cap?
        ├── yes → allowed
        └── no → block and notify
```

The cap must be enforced server-side in Production.

------------------------------------------------------------------------

# 40. Deduplication

Before applying:

``` text
same user
+
same company
+
within configured dedup window
```

must prevent duplicate application attempts.

Default requirement:

``` text
60 days
```

The exact policy must remain configurable.

------------------------------------------------------------------------

# 41. Responsible Rate Control

Production should enforce:

-   daily per-user cap
-   bounded concurrency
-   randomized interaction delays
-   bounded retries
-   no infinite retries
-   no uncontrolled browser spawning

Delays must not replace DOM-state synchronization.

Correct:

``` text
wait for DOM state
+ optional small randomized delay
```

Incorrect:

``` text
sleep 5 seconds
assume page is ready
```

# 58. Critical Acceptance Scenarios

## Scenario A --- Invalid URL

``` text
Given targets.txt contains an invalid URL
When the bot reads the file
Then it logs a warning
And continues to the next valid URL
```

## Scenario B --- Known Q&A

``` text
Given a real Workday question exists in the user's Q&A store
When the question is scanned
Then fuzzy matching selects the answer above threshold
And the value is applied
And the DOM verifies it
```

## Scenario C --- Unknown required question

``` text
Given a required real Workday question has no usable answer
When the engine reaches the field
Then it pauses
And requests human input
And persists the answer
And applies it
And verifies it
```

## Scenario D --- Compliance question

``` text
Given a compliance-sensitive question has no explicit human answer
When the question is encountered
Then the bot does not infer an answer
And requests a human-sourced answer
```

## Scenario E --- Dynamic page count

``` text
Given two Workday applications have different wizard steps
When the engine processes them
Then it scans each resulting page dynamically
And does not depend on a fixed page count
```

## Scenario F --- Review

``` text
Given the application reaches Review
When intended values are cross-checked
Then mismatches block submission
And matching values allow submission
```

## Scenario G --- Failure

``` text
Given an unexpected exception occurs
When the run fails
Then URL, timestamp, and stack are logged
And a screenshot is captured
And browser resources close cleanly
And the batch does not silently crash
```

## Scenario H --- Concurrent users

``` text
Given User A and User B run applications concurrently
When both encounter questions
Then each receives only their own Q&A and credentials
And neither user's pending question can be answered by the other user
```

# 59. Operational Guardrails

The bot must not:

-   bypass CAPTCHA using prohibited methods
-   defeat security controls
-   guess compliance answers
-   submit fabricated information
-   exceed configured application caps
-   apply without required Production user approval
-   reuse another user's credentials or answers
-   conceal failures

If a CAPTCHA or other blocking challenge prevents automation, classify
the run as requiring human review rather than attempting to circumvent
the security mechanism.
