# Implementation Plan — Workday Auto-Apply Bot

Stack: **Node.js + Playwright**. Two build tracks, sequential: Local Phase (3 sub-phases) then Production Phase. Each sub-phase ends in a real-URL checkpoint before moving on, per `AGENTS.md` discipline.

---

## 1. Phase Sequencing

```
Local-1 (link intake + auth)
   → Local-2 (DOM-first dynamic scan + fuzzy Q&A fill)
      → Local-3 (terminal fallback + learning + auto-submit)
         → [gate: reliable end-to-end run on ≥3 real Workday tenants]
            → Prod-1 (Telegram onboarding + credential auto-login)
               → Prod-2 (domain-matched job delivery + approval)
                  → Prod-3 (DB-driven Q&A resolution over Telegram)
                     → Prod-4 (status tracking, 2+ concurrent users)
```

Do not start a Production sub-phase until the Local Phase gate passes — Production Phase is a thin Telegram/Supabase shell around the same engine, not a parallel rebuild.

---

## 2. Local Phase — Task Breakdown

### Local-1: Link Intake & Auth
- [ ] `discovery.mjs`: read `targets.txt`, validate URLs, skip malformed with warning
- [ ] Reuse existing `workday.mjs` login/signup logic — integrate into new pipeline entry point
- [ ] Popup/interstitial detector for "Sign in with email" style modals
- [ ] Post-signup redirect detection (no blind retry-login)
- **Checkpoint:** Given a real Workday job URL requiring login, when `node cli.mjs apply <url>` runs, then the bot reaches the first form page authenticated, no manual click.

### Local-2: DOM-First Scan + Fuzzy Fill
- [ ] `scanner.mjs` / `workdayDom.mjs`: DOM + accessibility-tree field extraction per page
- [ ] Screenshot capture wired in parallel, explicitly not used for branching logic
- [ ] `qaStore.mjs`: local YAML-backed Q&A cache, fuzzy match (e.g. `fuzzysort` or `string-similarity` package) against `question_normalized`
- [ ] `planner.mjs`: factual-field fallback to `profile.yml` when cache misses
- [ ] Page-transition detection (heading/progress-bar/URL, not fixed sleeps)
- **Checkpoint:** Given a job with a known cached question, when the bot scans that page, then it fills the field correctly without prompting.

### Local-3: Fallback, Learning, Submit
- [ ] Terminal `input()` escalation for required fields with no source
- [ ] Persist new answer to `qa_answers` (local store) keyed by normalized question
- [ ] Skip-logic for optional/non-required unanswered fields
- [ ] Review-step cross-check + auto-submit
- [ ] CSV logging (`data/applied.csv`) + screenshot filenames per spec in `ui-ux.md`
- [ ] Full try/except wrapping with clean browser shutdown on failure
- **Checkpoint:** Given a job with one never-seen required question, when the bot hits it, then it pauses in terminal, accepts the typed answer, fills it, submits the application, and the same question is answered automatically on the next run for the same user.

**Local Phase Gate:** 3 different real Workday tenants applied to end-to-end with ≥80% no-manual-intervention rate (beyond first-time Q&A).

---

## 3. Production Phase — Task Breakdown

### Prod-1: Telegram Onboarding + Auto-Login
- [ ] Telegram bot registered via BotFather (see `telegram-bot-setup.md`)
- [ ] Deep-link token generation + QR rendering for onboarding
- [ ] `/start <token>` handler → resolve/create `telegram_links` row
- [ ] Email capture → resolve `users` row
- [ ] Fetch `workday_credentials`, decrypt, run existing `workday.mjs` login
- [ ] Send login-confirmation Telegram message
- **Checkpoint:** Given a QR scan + email reply, when onboarding completes, then the bot logs the correct Workday account in and confirms via Telegram — verified for 2 distinct test users without cross-contamination.

### Prod-2: Domain-Matched Delivery
- [ ] `job_links` query filtered by `users.domain`
- [ ] Telegram Apply/Skip inline buttons
- [ ] `applications` row created on approval (status `eligible` → `pending`)
- **Checkpoint:** User A (domain = software_engineer) never receives a `job_links` row tagged for a different domain; User B's queue is fully independent.

### Prod-3: DB-Driven Q&A Resolution
- [ ] Port `qaStore.mjs` logic to query Supabase `qa_answers` (pg_trgm fuzzy match, see `backend-schema.md` §4) instead of local YAML
- [ ] Resume-parse fallback (reuse existing resume-derived factual-field logic)
- [ ] Telegram escalation message + reply capture → insert new `qa_answers` row
- **Checkpoint:** A question unresolved by cache and resume is sent to the correct user's Telegram thread, and the reply is durably stored and reused on a subsequent, different job for the same user.

### Prod-4: Status Tracking & Multi-Tenancy
- [ ] `applications.status` lifecycle wired end-to-end (`pending → submitted/needs_review/rejected_ineligible/failed`)
- [ ] Daily cap + 60-day dedup enforcement (`backend-schema.md` §5) before queuing
- [ ] Result message sent to Telegram on completion
- [ ] RLS policies applied and verified
- **Checkpoint:** Running the full pipeline concurrently for 2 users produces correctly isolated logs, credentials, and Q&A stores, with no data crossing between them.

**Production Phase Gate:** 2 real users onboarded, each with at least one real end-to-end submitted application, fully DB-driven, no hardcoded per-user values anywhere in code.

## 4. Dependencies

```
qrcode            — QR generation for onboarding deep-link (Production Phase)
@supabase/supabase-js — Supabase client (Production Phase)
pgsodium / Supabase Vault — credential encryption at rest (Production Phase)
dotenv            — env var loading (both phases)
```

## 8. Flagged Open Questions — confirm before/while building

1. **QR mechanism**: Telegram has no native "scan-to-authenticate" for bots. The plan above uses a **deep-link QR** (`t.me/<bot>?start=<token>`) — scanning opens the Telegram app to a pre-filled chat with the bot, not an in-app QR scanner. Confirm this matches your intent, or clarify if you mean something else (e.g. a WhatsApp-Web-style paired-session QR, which Telegram Bot API does not support).
2. **Initial Workday credential capture**: where/how does a user's real Workday email+password first get into `workday_credentials`? (e.g. entered once via a secure onboarding form, or provided directly to you out-of-band for manual insert for the 2 pilot users?)
3. **Domain taxonomy**: should `domain` be a fixed controlled list (e.g. enum: `software_engineer`, `data_scientist`, ...) or free text matched loosely? Affects `job_links` tagging discipline.
4. **Job-link sourcing**: how does `job_links` get populated — manual entry by you for the pilot, or a scraper/API integration (out of scope per `prd.md` §4 unless you want it added)?
