# UI/UX Spec — Workday Auto-Apply Bot

This is not an end-user interface spec in the traditional sense — the "UI" here is (1) how the bot must read and interact with **Workday's own application UI**, and (2) how the bot communicates with the human across the two phases (terminal in Local, Telegram in Production). Both are specified so the IDE coding agent has an unambiguous interaction contract.

---

## 1. Workday Application UI — Structural Contract

Workday career-site application wizards vary by tenant/requisition, but share this shape. The bot must treat this as a **pattern**, not a fixed template — page order, page count, and question count vary per job.

### 1.1 Canonical stage set (may vary; detect, don't assume)
```
My Information → My Experience → Application Questions → Voluntary Disclosures → Review
```
- Progress indicator at the top reflects current stage (completed = filled, current = active, future = grey).
- Footer navigation is consistent: **Back / Save and Continue** on all steps except Review, which has **Back / Submit**.

### 1.2 Locator priority (strict order)
1. `getByRole()` with accessible name
2. `getByLabel()`
3. `[data-automation-id="..."]` (Workday's own stable attribute)
4. `getByText()` / `:has-text()` as last resort
5. **Never**: absolute XPath, screen coordinates, pixel positions, or CSS classes that look auto-generated

### 1.3 Field-type handling contract

| UI pattern observed | Required handling |
|---|---|
| Searchable/typeahead dropdown (e.g. country phone code) | Click to open → type search term → wait for options → select exact match |
| Multi-stage cascading dropdown (e.g. "How did you hear about us" → sub-category) | Select parent → wait for child options to populate (network/render delay) → select child |
| Radio group | Select by explicit value/label match, never by position |
| File upload (resume) | Locate the real `<input type="file">` (even if visually hidden) via `setInputFiles()` — never drive the OS file picker |
| Multi-value tag/skill input | Treat as combobox/autocomplete; do not assume plain text entry |
| Checkbox (consent/terms) | Click, then verify checked state before proceeding |
| Read-only prefilled field (e.g. email) | Do not attempt to overwrite |

### 1.4 Page-transition contract
- After **Save and Continue**, wait for the loading indicator to detach and for the next step's heading to render — never assume an immediate URL change.
- After every field interaction, prefer a bounded re-scan (e.g. MutationObserver-debounced) over fixed `setTimeout` sleeps.

### 1.5 Review-step contract
Before clicking Submit, verify:
1. Current heading is "Review".
2. Each major section (Information, Experience, Application Questions, Disclosures) is present and non-empty where required.
3. Resume is attached if required.
4. Consent/terms checkbox is checked.

Only then submit — then wait for a confirmation state/text before closing the browser.

## 2. Human-in-the-Loop UX

### 2.1 Local Phase — Terminal UX
When the bot cannot answer a required question:
```
──────────────────────────────────────────
⚠ Unknown required question
Company:  <company>
Question: "<verbatim question text>"
Field type: <dropdown|text|radio|...>
Options (if applicable): [...]
──────────────────────────────────────────
> Your answer:
```
- Bot blocks on this single field only — does not abandon the run.
- Once answered, the bot echoes back what it filled and continues automatically (no further confirmation needed unless `--confirm-submit` is set).
- At the very end of a run, print a one-line summary: `✅ Submitted | ⚠ Needs review | ❌ Failed` per URL.

### 2.2 Production Phase — Telegram UX

**Onboarding**
```
[QR code image]
"Scan to connect your job-search assistant."
→ user scans → opens chat → bot: "What's your email?"
→ bot resolves user record → "You're linked ✅. Logging into Workday now…"
→ "You're logged in ✅"
```

**Job match notification**
```
🆕 New match for you (Software Engineer)
<Role title> @ <Company>
[Apply]  [Skip]
```

**Unknown question escalation**
```
🤔 One question I couldn't answer for <Company>:
"<verbatim question text>"
Reply with your answer — I'll remember it for all future applications.
```

**Result notification**
```
✅ Applied: <Role> @ <Company>
— or —
⚠ Needs review: <Role> @ <Company> — <reason>
— or —
❌ Failed: <Role> @ <Company> — see logs
```

### 2.3 Tone & constraints for all human-facing messages
- Never expose raw selectors, stack traces, or internal field IDs to the end user (Production Phase) — plain language only.
- Compliance-sensitive questions (work auth, visa, EEO) are always flagged distinctly (e.g. 🔒 prefix) so the user understands why it's being asked directly rather than auto-filled.
- Every escalation must state clearly that the answer will be **remembered permanently** for that user, so the user understands they won't be asked again.

## 3. Audit/Screenshot UX (non-interactive, but part of the "UI" contract)
- One screenshot immediately before Submit, one immediately after (or after failure).
- Screenshot filenames: `{company}-{role-slug}-{timestamp}-{pre|post}.png`
- Screenshots are for human audit only — the bot must never branch logic based on screenshot content.
