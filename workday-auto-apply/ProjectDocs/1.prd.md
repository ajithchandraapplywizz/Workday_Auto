# PRD — Workday Auto-Apply Bot
* · **Stack:** Node.js + Playwright · **Status:** Draft v1 · **Scope:** Workday ATS only

---

## 1. Vision

A bot that applies to jobs on live Workday-hosted career sites with zero manual form-filling, starting as a single-user local CLI tool (Local Phase) and evolving into a multi-user Telegram + Supabase service (Production Phase) that discovers eligible jobs, notifies the user, and applies on approval.

## 2. Problem Statement

Workday is the hardest ATS to automate because:
- Every company's Workday tenant has a **different question set, different page count, and sometimes different login/signup flow.**
- Screenshots/vision-based filling is slow, fragile, and expensive to run at volume.
- Naive auto-submit on compliance-sensitive questions (work authorization, visa, EEO) creates legal/accuracy risk.
- There is no single fixed "form shape" — the wizard is dynamic per job requisition.

## 3. Goals

| # | Goal |
|---|---|
| G1 | Apply to a live Workday job end-to-end (login → fill → review → submit) without manual clicking |
| G2 | Handle **any** Workday tenant's dynamic wizard, not one hardcoded flow |
| G3 | Never fabricate an answer — pull from profile/resume, ask the user once, then remember forever |
| G4 | Scale from 1 user (local terminal) to N users (Telegram-driven, Supabase-backed) without rewriting the core engine |
| G5 | Full auditability — every field filled, every answer sourced, every submission logged |

## 4. Non-Goals (Out of Scope)

- Non-Workday ATS platforms (Greenhouse, Lever, Ashby, iCIMS, SmartRecruiters) are explicitly **removed** from this build. Prior multi-ATS code is reference-only and not to be reused.
- Vision/screenshot-based field detection as the primary filling method (screenshots are for **audit logging only**).
- Auto-answering compliance-sensitive questions without a first-time human answer on record.
- Resume rewriting/tailoring content generation (may be a future phase, not this one).

## 5. Users

| Persona | Description | Phase |
|---|---|---|
| **Operator (Pintu)** | Runs the bot from terminal, watches the browser, answers unknown questions once | Local |
| **End User (job seeker)** | Has a Telegram account + Workday credentials on file; approves job matches via Telegram; never touches code | Production |

## 6. Scope by Phase

### 6.1 Local Phase (single user, terminal-driven) — 3 sub-phases

**Local-1 — Link intake & auth**
- Reads a list of job links from a file.
- Opens each link in a **visible (headed)** browser.
- Auto sign-in using existing account-creation/login logic (already built — reused, not rebuilt).
- Detects and handles login/signup popups and interstitials (e.g. "Sign in with email") and auto-clicks the correct path, entering stored credentials.

**Local-2 — DOM-first dynamic form handling**
- Every page is read via **DOM/accessibility tree**, not screenshots. Screenshots are captured in parallel purely for audit/record-keeping.
- Handles the core conflict: **page count and question set vary per application** — no fixed step map.
- Before filling, scans the DOM for all questions on the current page.
- Matches each scanned question to a cached Q&A store using **fuzzy matching** (approximate string match, not exact) to fetch the known answer.
- For fields the fuzzy match misses, falls back to resume-derived inference for factual fields (name, education, experience) — never invents new facts.

**Local-3 — Fallback, learning loop, and submission**
- If no answer is found anywhere (cache miss + resume miss), the bot **pauses and asks the operator in the terminal**, takes the typed answer, uses it to fill the field, and **persists the question+answer pair** for that user so it's never asked again.
- Unimportant/optional questions are skipped automatically.
- After each page's important fields are filled, auto-clicks through (Save & Continue / Next).
- At the final Review step, cross-checks entered values, then **auto-submits**.

### 6.2 Production Phase (multi-user, Telegram + Supabase-driven)

**Prod-1 — Telegram onboarding & credential-backed login**
- User scans a QR (deep-link into the Telegram bot) and provides their email.
- The bot already holds that user's Workday email/password in Supabase (entered once at onboarding) — it retrieves it and logs the user into Workday automatically.
- Telegram message confirms: *"You're logged in."*

**Prod-2 — Domain-matched job delivery**
- Based on the user's stored domain/role preference (e.g. "Software Engineer"), the bot selects matching links from a Supabase-held pool of job links tagged by domain — **never sends links outside the user's domain.**
- User is notified via Telegram and approves before the bot applies.

**Prod-3 — Unknown-question resolution (DB-driven)**
- New question on a form → fuzzy-match against Supabase Q&A table for that user → if no match, attempt resume parsing → if still unresolved, **send the question to the user over Telegram**, capture their one-time reply, and permanently store it as a new Q&A row tied to that user for all future applications.

**Prod-4 — Status tracking**
- Every application's outcome (submitted / needs-review / rejected-ineligible / failed) is written back to Supabase and reflected in the Telegram thread.
- Must support **at least 2 concurrent users** cleanly (multi-tenant data model, not single global config).

## 7. Success Metrics

| Metric | Local Phase target | Production Phase target |
|---|---|---|
| End-to-end submit success rate on a real Workday job | ≥ 80% without manual intervention beyond first-time Q&A | ≥ 80% per user |
| Unknown-question recurrence | 0 — a question asked once is never asked again for that user | Same |
| Fabricated/incorrect compliance answers | 0 | 0 |
| Concurrent users supported | 1 | ≥ 2, isolated data |

## 8. Constraints & Assumptions

- Browser is **always headed** (`headless: false`) in Local Phase for operator supervision.
- No use of OCR/pixel/vision-based scanning as the primary decision mechanism.
- All secrets (Workday credentials, Telegram bot token, Supabase keys) live in environment variables / encrypted-at-rest DB columns — never hardcoded.
- Node.js + Playwright is the enforced stack for this build (superseding the earlier Python prototype referenced in prior planning).

## 9. Open Questions (flagged, not assumed — see implementation.md §9)

- Exact QR-linking mechanism (Telegram has no native "scan-to-login" for bots — this will be a deep-link QR, confirm before build).
- Where/how initial Workday credentials are captured for storage (one-time secure entry flow needs definition).
- Definition of "domain" taxonomy for job-link matching (fixed list vs free text vs resume-derived).
